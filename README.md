# Моя переносимая сборка Pi

Общий набор для дома и работы плюс локальный рабочий слой. Это конфигурация и исходники, а не копия установленного Pi, credentials или истории.

## Установка дома одной командой

Скачай/клонируй этот репозиторий в отдельную папку и из неё выполни:

```sh
./setup --profile home
```

Скрипт подключает наш локальный Pi package, устанавливает Pi **1.1.0** при отсутствии совместимой установки, загружает внешние npm-расширения точных версий из `config/settings.base.json`, формирует настройки и инструкции. Нужны macOS/Linux и доступ к npm; Node.js >=22.19. Если Node отсутствует, запускается официальный установщик Pi для установки prerequisites. Его диалог может потребовать участия пользователя. Нативный Windows пока не поддерживается скриптом.

Запуск после установки:

```sh
~/.pi/agent/bin/pi-config
```

В Pi выполни `/login`, затем `/model`: авторизация остаётся личной и не переносится с другого компьютера. Скрипт не меняет shell profile; при желании добавь `~/.pi/agent/bin` в PATH самостоятельно.

**Домашний профиль не подключает `work/`, внешний рабочий harness и управляемую интеграцию PAIW.** Репозиторий-источник остаётся на месте: не удаляй его после setup. Для изоляции укажи другой каталог:

```sh
./setup --profile home --agent-dir "$HOME/.pi/home-agent"
```

Если настройки уже существуют и ещё не управляются этой сборкой, setup откажется менять их без явного `--adopt`. Сначала посмотри `--dry-run`. Credentials, models.json, mcp.json и sessions не копируются и не редактируются.

## Рабочий профиль

`work/` целиком локальный и исключён из Git. Существующие рабочие скиллы и extensions здесь сохранены. Рабочие модель/провайдер и внешние пакеты задаются в локальном `work/settings.json`. Credentials остаются в обычном защищённом хранилище Pi.

```sh
./setup --profile work --dry-run
./setup --profile work --adopt
```

На новом рабочем компьютере рабочий слой и его инфраструктуру нужно подготовить отдельно: из домашнего репозитория они не приезжают. `work/settings.json` обязателен для этого профиля. Не подключай весь рабочий внешний пакет в базовом конфиге.

`--adopt` разрешает подключить сборку к существующим настройкам: личные поля сохраняются, известные npm-пакеты переводятся на версии базового конфига без дубликатов. Изменяемые файлы сохраняются в `backups/config-*`. Блок инструкций PAIW не перезаписывается: обновляется только собственный блок `PI CONFIG`.

Повторный setup идемпотентен. Ручные изменения обычных настроек сохраняются; версии пакетов, которыми управляет база, определяются базовым конфигом. Для смены home/work используй отдельный `--agent-dir`, а не переключение рабочего конфига на месте.

## Namespace-команды скиллов

```text
/pi:code-review
/pi:tester
/pi:curler
/pi:docs-loader
/pi:standby
/pi:skill-creator create <описание>
/pi:skill-creator create work <описание>
/pi:to-work skill example

/work:test
/work:read-task
/work:mr-check

/other:pdf
```

- `pi` — наши общие скиллы из `skills/`, кроме управляемого `skills/paiw/`.
- `work` — наши скиллы из `work/skills/`; старые имена `*-oneab` сохраняются.
- `other` — остальные подключённые скиллы. Привычный `generic-` сокращается только при свободном коротком алиасе; при конфликте сохраняется полное имя: `/other:pdf` и `/other:generic-pdf`. Источники не изменяются.

Алиасы и автодополнение обнаруживаются автоматически по расположению, включая вызов внутри сообщения. `/pi:tester` → `/skill:tester`. Имена каталогов и name не содержат обязательных префиксов. Нативный вызов остаётся доступен. При конфликте алиас блокируется; одинаковые нативные имена между разными источниками Pi могут конфликтовать ещё при загрузке. Проверяй диагностику; префиксы автоматически не добавляются. Вызовы внутри backtick-кода не раскрываются. Один скилл на сообщение.

`other` не устанавливает сторонние скиллы самостоятельно. Существующий `skills/paiw/` остаётся локальным управляемым каталогом; его симлинки не публикуются и не переносятся домой.

## Атомарные расширения

Каждый extension — самостоятельная папка `extensions/<name>/` с `index.ts`. Его helper-файлы лежат внутри; общей `lib/` и импортов из соседних расширений нет. Рабочие extensions устроены так же в `work/extensions/`.

Чтобы перенести один extension, скопируй всю его папку в `~/.pi/agent/extensions/` другой установки Pi и выполни `/reload`. Корневой package.json этой сборки для текущих расширений не требуется: SDK предоставляет сам Pi.

`compact-footer` работает без остальных extensions; статусы лимитов, времени, IDE и LSP использует только при их наличии. `inline-skill-autocomplete` работает без footer; при совместной загрузке они согласуют редактор через необязательный event-протокол, без импорта чужого кода. Небольшой editor-helper намеренно локален для каждого из них.

`codex-footer` использует личную авторизацию Pi/Codex и необязательный локальный `codex-footer.json`; credentials вместе с extension не переносятся.


## Добавление и перенос компонентов

Полные правила — в `AGENTS.example.md` и `/pi:skill-creator`.

Явный `create`/«общий» выбирает общий слой; `create work`/«рабочий» — рабочий. Без режима агент определяет категорию по обязательным зависимостям и спрашивает при неоднозначности. Явное указание не переопределяется молча.

Каркасы, которые нужно заполнить:

```sh
node scripts/components.mjs new skill example
node scripts/components.mjs new skill example --work
node scripts/components.mjs new extension example
node scripts/components.mjs new extension example --work
```

Оба режима создают каталог/name `example`: `skills/example/` для общего и `work/skills/example/` для рабочего. Категория определяется расположением, а не именем. Одинаковые нативные имена в двух слоях не допускаются: скрипт предупредит о конфликте. Все файлы компонента держи вместе; ссылки на references/scripts/assets делай относительными. Незавершённые скиллы с TODO не проходят проверку.

Перенос сначала показывает план, затем применяется **после согласования**:

```sh
node scripts/components.mjs to-work skill example
node scripts/components.mjs to-work skill example --apply
```

Можно использовать `/pi:to-work`. Скрипт проверяет пути, симлинки, конфликты назначения, ссылки и внешние относительные импорты. При зависимостях, требующих переписывания, останавливается: нужен отдельный согласованный план. Поиск зависимостей консервативный, не полноценный анализатор кода. Публикация и обратный перенос не выполняются автоматически.

Служебные `to-work` и `skill-creator` остаются общими; скрипт не переносит их в work.

**Новый компонент не требует отдельной записи** в `.gitignore`, манифесте или namespace-extension. Каталоги и маска `skills/*/SKILL.md` определяют состав; управляемый `skills/paiw/` исключён отдельно. После локальной правки используй `/reload`.

Внешние npm-расширения и точные версии добавляй только в `config/settings.base.json`. При добавлении runtime-зависимостей своего extension объявляй их в его локальном `package.json` и согласуй установку. Библиотеки, которые предоставляет Pi, — только `peerDependencies`. Установщик не дублирует список внешних пакетов.

## Обновление

После commit/push изменений из чистого клона:

```sh
./setup --profile home --update
# на рабочем компьютере:
./setup --profile work --update
```

Сначала выполняется `git pull --ff-only`, затем повторное развёртывание. Грязный checkout не обновляется. Если изменения уже получены вручную, достаточно setup без `--update`. Фонового обновления при каждом запуске Pi нет. Прямые версии фиксированы, но npm-пакеты могут иметь собственные транзитивные диапазоны: это не lock всей сторонней инфраструктуры.

## Проверки и публикация

```sh
npm run check
```

`npm run check` проверяет переносимость общих компонентов и границы локального рабочего слоя.

`--dry-run` не пишет конфиги и не скачивает пакеты. `--skip-install` настраивает профиль без установки runtime/npm-пакетов — это режим для офлайн-проверок, не доказательство полной установки на чистом компьютере.

В Git входят общие исходники, шаблоны и документация. Не входят `work/`, живые конфиги, AGENTS.md с локальными инструкциями, secrets, sessions, backups, install, npm, node_modules и управляемые скиллы.

Перед первым коммитом и публикацией прочитай [чеклист](docs/publishing.md). Автоматическая проверка не гарантирует отсутствие всех секретов и не проверяет право публиковать сторонний код. Не публикуй сессии и рабочие файлы. Коммит и push требуют отдельного согласования.
