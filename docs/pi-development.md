# Разработка компонентов Pi

Правила относятся к исходникам этой сборки, не к прикладному проекту из текущего cwd. Слой и размещение выбираются по [правилам сопровождения](pi-maintaining.md).

## Скилл, агент или extension

- Скилл описывает сценарий: входные данные, шаги, разрешения, результат и остановки. Его инструкции загружаются по необходимости, а не целиком в системный промпт.
- Профиль агента задаёт специализацию, инструменты и контекст дочернего исполнения. Общие правила проверки не копируются в профиль: агент читает исходный скилл.
- Extension добавляет исполняемую возможность, которую нельзя надёжно обеспечить инструкцией: инструмент, обработчик события или UI. Не создавай extension для каждого flow и не строй универсальный движок заранее.

Перед реализацией прочитай документацию и связанные примеры установленной версии Pi. Версия runtime этой сборки задана в `package.json`, зависимости — в конфигурации и локальных manifests.

## Extensions

- Один компонент — одна реальная папка с `index.ts` и локальными helpers. Компонент должен переноситься целиком.
- Не импортируй код соседнего extension или общей `lib/`. Выделяй повторяющийся механизм только после появления реальной второй потребности, а не предполагаемой архитектуры.
- Фабрика регистрирует API; побочные действия привязываются к подходящему событию или явному вызову инструмента. Обрабатывай отмену и освобождение временных ресурсов.
- Credentials не должны попадать в контекст модели, аргументы процессов, логи или чат. При необходимости передавай согласованные ссылки на файлы; значения загружает исполняемый код внутри своей границы. Не используй настоящие секреты в примерах и фикстурах.
- Не выдумывай события, инструменты и поля API. Текстовая просьба к модели не заменяет исполняемое переключение режима или проверку разрешений.
- Используй штатные интерфейсы Pi; учитывай другие установленные редакторы и расширения. Не заменяй базовый системный промпт ради локального правила.
- Runtime-зависимости объявляются в локальном `package.json` компонента; установку согласуй. Host-пакеты Pi остаются `peerDependencies`, а не копируются внутрь extension.
- Внешние npm-extensions подключаются в `config/settings.base.json` с точной версией. Обязательные рабочие зависимости относятся к рабочему слою.

## Скиллы и разрешения

Перед созданием или изменением компонента проверь доступные инструкции по их актуальным описаниям и условиям применения. Загружай только подходящие к задаче; не закрепляй в общих правилах имена вспомогательных скиллов или их неизменный набор.

- Минимальный frontmatter: `name`, содержательный `description`, явное `disable-model-invocation`. Имя совпадает с каталогом и не конфликтует с подключёнными нативными именами.
- Скилл с `disable-model-invocation: false` можно выбрать по контексту разрешённой задачи или по прямому запросу обычным текстом. Slash-команда не обязательна. В описании укажи точные условия применения, чтобы скилл не добавлял собственную задачу к чужому запросу.
- `disable-model-invocation: true` скрывает метаданные от автовыбора; используй его для компонентов, которым действительно нужен вход по команде. Не путай «только по просьбе пользователя» с «только по slash-команде»: прямой естественный запрос тоже может разрешать действие. Разрешения и обязательные подтверждения задаются контрактом, а не этим флагом. Не включай самостоятельный трековый Flow для каждой мелкой задачи.
- Подключение инструкций не разрешает новые правки, запуск агентов или инфраструктуры, внешние мутации, коммиты и публикацию. Уже полученное разрешение повторно не запрашивается; существенное расширение объёма обсуждается отдельно.
- Не меняй поведение сторонних и управляемых Generic/PAIW-скиллов вместе с нашими.

Сценарий проверки хранится в одном исходном `SKILL.md`. Ссылки и ресурсы компонента — в его `references/`, `scripts/`, `assets/`.

## Агенты и отчёты

- До создания профиля выбери общий или рабочий слой так же, как для скилла или extension. Наличие агента не разрешает его запуск; `async: true` означает фоновый режим запуска, не автозапуск.
- Профиль должен быть тонким: роль, необходимые инструменты, контекст и ссылка на правила исполнения. Не закрепляй одну архитектуру агентов для всех будущих flow.
- Отчёт пользователю возвращается текстом в чат, обычно 3–7 строк: статус, область, существенный результат, ошибка или blocker и ограничения. Не скрывай важные проблемы ради размера отчёта.
- Не заменяй результат ссылкой на файл и не создавай файлы отчётов по умолчанию. Для `pi-subagents` используй `outputMode: inline` без `output`; файл допустим только по отдельному запросу.
- Служебные сессии и логи раннера — не пользовательский отчёт. Не выгружай в чат длинные трассировки или секреты; дополнительные подробности предоставляй по необходимости.

Детали конкретного workflow хранятся в его собственном контракте. Общие правила разработки не зависят от названий скиллов или фиксированного списка исполнителей.

## Проверки без лишней инфраструктуры

- После изменения запускай `node scripts/check-portability.mjs`, доступную проверку типов или синтаксиса и проверку затронутого поведения.
- Не заводи тестовый framework, новый набор зависимостей или обязательное покрытие ради каждого скилла, профиля и UI-хука. Не создавай `tests/` и `work/tests/` без запроса.
- Для Markdown-инструкций обычно достаточно чтения, проверки frontmatter и ссылок. Не закрепляй дословные формулировки и структуру текста unit- или snapshot-тестами.
- Для исполняемой логики extensions точечные тесты полезны там, где снижают реальный риск: credentials, разрешения, пути, HTTP, отмена и восстановление состояния. Не раздувай набор искусственными вариациями.
- Существующий `npm run check:verification` проверяет код runtime и интеграцию с SDK на фиктивных данных, без вызовов модели. Используй его при изменении соответствующей логики, не превращая его в требование для любой правки текста.
- Успешная загрузка или проверка типов не доказывает реальное выполнение агента. Для такого smoke-test отдельно согласуй запуск, окружение и расход модели. Не используй настоящие credentials в тестовых фикстурах.

В отчёте различай свежий запуск, кэш, статический анализ и ручную проверку. После обновления компонентов предложи `/reload`; не коммить и не публикуй автоматически.
