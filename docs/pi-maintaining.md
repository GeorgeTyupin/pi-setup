# Сопровождение сборки Pi

Это правила устройства, обновления и публикации самой сборки. Реализация компонентов и соразмерные проверки описаны в [pi-development.md](pi-development.md).

## Два слоя

| Компонент | Общий, переносимый | Рабочий, локальный |
|---|---|---|
| Скилл | `skills/<slug>/SKILL.md`, `/pi:<slug>` | `work/skills/<slug>/SKILL.md`, `/work:<slug>` |
| Extension | `extensions/<slug>/index.ts` | `work/extensions/<slug>/index.ts` |
| Профиль агента | `agents/<name>.md` | `work/agents/<name>.md` |

Общий слой хранится в Git и входит в переносимый пакет. `work/` не коммитится и не публикуется; рабочие компоненты, настройки и backups переносятся отдельно владельцем. Рабочий профиль подключает локальный рабочий слой поверх общего, а не заменяет его.

Общие компоненты не содержат credentials, внутренних адресов, жёстких путей пользователя и обязательных корпоративных зависимостей. Локальная настройка не должна незаметно превращаться в требование переносимой сборки.

### Выбор до создания

1. Возьми назначение и обязательные зависимости из запроса и уже известного контекста. Не спрашивай то, на что ответ уже есть.
2. Явные `create` / «общий» выбирают общий слой, `create work` / «рабочий» — рабочий. Если явный выбор противоречит обязательной рабочей зависимости, объясни это и уточни решение, не меняя слой молча.
3. Без явного выбора переносимая задача без обязательной корпоративной привязки относится к общему слою. Внутренние сервисы, корпоративные инструменты, обязательные рабочие правила и инфраструктура означают рабочий слой.
4. Сам факт использования на работе, Git или обычной авторизации по JWT не делает компонент рабочим. Существенна обязательная привязка к конкретной организации.
5. При неоднозначности задай один вопрос: «Создать общий или рабочий компонент?» До записи покажи выбранный слой, путь и основание выбора.

Правило одинаково для скиллов, extensions и агентов. Например, универсальные роли ревью, запуска тестов и локальной HTTP-проверки — общие; специалист, которому обязательно нужен внутренний сервис, — рабочий. Не переноси существующий компонент между слоями без согласования.

### Имена и обнаружение

Категория задаётся расположением, не префиксом имени. У нативных скиллов Pi единое пространство имён: проверяй конфликты со всеми подключёнными скиллами. Существующие рабочие имена с `-oneab` сохраняются; команда `/work:` сокращает этот суффикс. Сторонние ресурсы остаются в `/other:`.

Каркас скилла или extension создаётся через `node scripts/components.mjs new <skill|extension> <slug>`; после выбора рабочего слоя добавь `--work`. Каркас агента пока создаётся вручную. CLI не заменяет выбор слоя и согласование контракта.

Новые наши скиллы и extensions обнаруживаются по каталогам: не добавляй каждому отдельную запись в manifest, gitignore или namespace-extension. Общие агенты обнаруживаются из `agents/` и пакетной записи `pi-subagents.agents`.

Для будущего рабочего агента недостаточно создать `work/agents/`: подключи этот каталог через `subagents.agentScanDirs` в локальных настройках рабочего профиля, не в общем manifest. Используй абсолютный или `~/` путь к каталогу в локальных исходниках; не полагайся на разрешение относительных путей раннером. В общем профиле такого подключения быть не должно. Общий/рабочий слой не равнозначен runtime-параметру `agentScope: user/project`.

Для переноса общего скилла или extension выбери подходящую доступную процедуру по её назначению либо сначала выполни preview `node scripts/components.mjs to-work <skill|extension> <имя>`, затем согласованный `--apply`. Не требуй наличия скилла с конкретным именем. Перенос профилей агентов пока ручной, с проверкой ссылок и подключения.

## Источники инструкций

- `AGENTS.md` — короткий маршрут к применимым правилам, не копия всех процедур.
- Блок `PI CONFIG` генерируется из `scripts/setup.mjs`; исправляй источник, иначе обновление вернёт старый текст.
- Существующий текст вне `PI CONFIG`, в том числе управляемый блок PAIW, сохраняется. Не редактируй управляемые PAIW-источники и не копируй их в переносимую сборку.
- Алгоритм конкретного скилла хранится в его `SKILL.md`. Профили агентов ссылаются на исходные правила, не создавая вторую версию.
- При сопровождении не привязывай общие правила и инструкции разработки к конкретным именам скиллов или агентов и не закрепляй их неизменный набор. Выбирай подходящие инструкции по актуальным метаданным, назначению и контексту. Конкретные имена допустимы в описании самого компонента, снимке каталога или специализированном workflow с явной зависимостью, но не как обязательный список для любой разработки.

## Обновление на другом компьютере

Команда установки из [README](../README.md) также обновляет уже настроенную сборку. Проверяется сохранённый профиль в `pi-config-state.json`.

- **Общий профиль (`home`)**: CLI получает актуальный SHA ветки `main` из GitHub, загружает архив этого SHA и использует свежий установщик. Кэш старого bootstrap-пакета `npx` не фиксирует версию исходников.
- **Рабочий профиль (`work`)**: CLI использует локальный checkout из `sourceRoot`, требует чистое Git-состояние и ветку `main`, затем выполняет `git pull --ff-only`. Подтягивается общий Git-репозиторий; игнорируемый локальный `work/` не загружается с сервера и не публикуется.
- После этого обновляются управляемые настройки, инструкции и launcher; при необходимости устанавливается закреплённый Pi runtime и обновляются подключённые пакеты. Пользовательские настройки сохраняются в пределах правил слияния, перед изменением файлов создаются локальные backups.
- На другом устройстве появятся только изменения, уже отправленные в его источник обновления — обычно `main`. Незакоммиченная правка и локальный коммит без push там не появятся.
- Частные `work/`, credentials, provider/model-привязки и живые конфиги не входят в общую поставку. Они должны быть настроены на каждом устройстве отдельно.

Перед обновлением рабочего checkout сохрани его изменения согласованным способом; установщик не делает автоматический stash или reset. Для смены профиля нужен отдельный `--agent-dir`.

`--no-launch` обновляет без запуска Pi. `--dry-run` показывает план без применения настроек, но в общем профиле может загрузить свежие исходники. Явный `--source-root` применяет указанный локальный источник без автоматического pull. `--skip-install` пропускает установку runtime и пакетов, поэтому не равнозначен полному обновлению.

`pi update` обновляет подключённые пакеты и не заменяет установщик сборки. Launcher `pi-config` только запускает уже выбранный runtime. После изменения загруженных ресурсов используй `/reload` или перезапуск.

## Аудит и подготовка коммитов

1. Сначала проверь `git status`, tracked/untracked файлы и конкретный diff. Сохраняй изменения пользователя; не создавай ветку и не делай staging автоматически.
2. Раздельно перечисли наши скиллы, профили агентов и extensions. Generic/PAIW и встроенные профили стороннего раннера не считай нашими компонентами.
3. Для скиллов проверяй `disable-model-invocation` и применимые hooks, а не только описание. Для агентов отдельно укажи контекст и условия разрешённого запуска: наличие профиля или `async: true` не является автозапуском.
4. Предложи логические коммиты с короткими сообщениями на русском и составом. Создавай их только после просмотра и разрешения пользователя. Push и публикация — отдельное действие.
5. Проверяй Git и состав npm-пакета независимо: локальный файл может быть не в коммите, но попасть в архив из рабочего дерева.

`extensions/subagent/` принадлежит локальному состоянию стороннего `pi-subagents`, а не исходникам нашего extension. Не удаляй его конфиг; он исключается из Git, Pi-ресурсов и переносимого пакета. Аналогично не включай локальную стороннюю интеграцию `idea-selection`.

Перед публикацией следуй [проверке состава и прав](publishing.md). Не считай gitignore защитой от уже опубликованного секрета и не выдавай базовый portability-check за полный аудит безопасности или лицензий.
