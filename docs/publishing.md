# Перед первой публикацией

1. Выполни `npm run check` и доступную статическую проверку. Папки тестов удалены из сборки; не воссоздавай их без запроса.
2. Проверь `git status --short` и `git ls-files --others --exclude-standard`: в составе не должно быть work/, credentials, живых конфигов, локального AGENTS.md, истории, установленного Pi или управляемых симлинков.
3. После явного разрешения на staging проверь конкретный `git diff --cached`, а не только .gitignore. Уже отслеживаемые файлы не перестают отслеживаться от добавления ignore-правила.
4. Выполни полноценную проверку секретов принятым инструментом. Наш checker ищет только известные признаки, а не доказывает отсутствие чувствительных данных.
5. Проверь источник, права на копирование и требования атрибуции каждого стороннего файла. Новая общая лицензия не назначена автоматически. При отсутствии подтверждённых прав исключи компонент из публикации и переносимого набора.
6. Наша домашняя база не содержит рабочий внешний harness. Никакие его модули не копируются в общий слой автоматически.
7. Для проверки чистой установки используй отдельный checkout только опубликованных файлов и отдельный `--agent-dir`. Не копируй всю ~/.pi/agent.
8. Определи hosting, адрес remote и видимость репозитория. Сейчас наличие локального Git не означает, что он опубликован.
9. Только после согласования состава создай коммит, затем отдельно push. Рабочий слой останется только на этом компьютере и в его локальных backups.

Перенос когда-то опубликованного компонента в work/ не стирает его из истории. При утечке секрета сначала отзови его; очистка истории является отдельной согласованной операцией.
