# Verification runtime

Техническая поддержка `/pi:verify`, `/pi:code-review`, `/pi:tester`, `/pi:curler`. Порядок и критерии проверок находятся в `SKILL.md`, общий режим запуска — в `skills/verify/references/execution.md`; расширение не дублирует их и само не запускает агентов.

## Инструменты

- `verification_options` — детерминированный разбор флагов и проверка ответов ask. Возвращает `missing`, поддерживаемый effort, пути к исходным скиллам и роли. Не исполняет проверку.
- `verification_effort` — временный реальный thinking level для inline-ревью: `begin` → `lease` → `end`. Смена модели/уровня пользователем не перетирается. Незакрытый lease восстанавливается при `agent_settled`/shutdown. Для субагента используется `model` с суффиксом уровня, а не этот инструмент.
- `verification_auth` — читает только безопасный JSON-указатель и проверяет file references, **не читает значения credentials**.
- `verification_curl` — вызывает системный curl через `http.mjs`, без shell. Загружает credentials внутри кода, отдаёт curl приватный файл заголовков и возвращает только очищенный результат.

Runtime-зависимости npm не добавляются. Нужны host-пакеты Pi и установленный `curl`. Установка/обновление пакетов, запуск приложения и изменения БД автоматически не выполняются. После изменения — `/reload`.

## Указатель авторизации

Можно передать явный `jwtFile`, либо `configFile`. Без них ищется ближайший `<repo>/.paiw/verification.json` по пути от cwd вверх (не выше домашнего каталога), затем необязательный `~/.paiw/resources/personal/verification.json`. Отсутствие указателя — `blocked`, а не анонимный запрос. Файлы не создаются автоматически, весь PAIW не сканируется.

Пример **метаданных**, не токена:

```json
{
  "baseUrl": "http://127.0.0.1:8080",
  "jwtFile": "./credentials/local.jwt"
}
```

Пути внутри указателя разрешаются относительно самого указателя; поддерживаются абсолютные пути и `~/`. `jwtFile` должен содержать только один JWT. Если существующий документ PAIW содержит JWT вместе с текстом, модель не должна его открывать: пользователь подготавливает отдельный credential-файл или явно согласованный формат. Указатель не заменяет token store и не должен содержать inline-secrets.

Другая схема допустима только после явного согласования и передачи пользователем ссылок на credential-файлы:

```json
{
  "authMode": "headers",
  "headerFiles": [
    { "name": "Authorization", "file": "./credentials/authorization.txt" },
    { "name": "X-Api-Key", "file": "./credentials/api-key.txt" }
  ]
}
```

В headers-режиме файл содержит полное значение соответствующего заголовка (например, с нужной схемой). `authApproved: true` в вызове означает уже полученное согласие пользователя. Дополнительные `headerFiles` можно применять и вместе с JWT, кроме повторного Authorization; они также требуют явного согласования и `authApproved: true`. Неподдерживаемая/недостающая схема не угадывается. Стандартного fallback без авторизации нет.

## Проверка реализации

Из корня сборки: `npm run check:verification`. Проверки используют только фиктивные credentials, локальный HTTP-сервер и установленные Pi SDK / pi-subagents; модели не вызываются, настоящие credential-файлы не читаются. Проверяются также реальный loader расширений и discovery профилей из user-каталога и package metadata.

По умолчанию SDK берётся из `install/releases/<piRuntimeVersion>/node_modules/@earendil-works/pi-coding-agent`; при другом расположении задай `PI_PACKAGE_DIR` — каталог пакета SDK. pi-subagents ищется в `npm/node_modules` текущего `PI_CODING_AGENT_DIR` (стандартно `~/.pi/agent`). Новые зависимости команда не устанавливает.

## Безопасность HTTP

- Только HTTP(S) localhost/127.0.0.1/::1; localhost явно привязывается к loopback. Credentials в URL запрещены. Redirect не исполняется.
- curl запускается без curlrc, proxy, verbose, tracing и отключения TLS-проверки. Значения credentials не попадают в argv; shell substitution не используется.
- Папка временного запуска приватная; заголовки и сырой ответ имеют mode 0600 и удаляются в `finally`. Остаётся только очищенный `report.json` вне репозитория. Timeout и размер ответа ограничены.
- В ответе маскируются использованные credentials, JWT-подобные строки и поля авторизации/секретов. Не выводятся response headers или сырой transport exception.
- Изменяющие HTTP-методы требуют `mutationApproved: true`, что означает ранее полученное разрешение, а не даёт новое. Неожиданный 401/403 — blocker для связанных сценариев.
- После разрешения file references runtime блокирует прямой `read`/контентный поиск известных credential-файлов. У curler строгий allowlist без bash, grep, произвольных HTTP/MCP-инструментов или записи. Это ограничение Pi-tools, **не OS sandbox**: сторонние расширения и код запускаемых тестов остаются доверенной частью среды.

Нельзя открывать токены моделью ради диагностики, включать сырые тела в отчёт или отправлять логи во внешние сервисы. Воспроизведение — повторный вызов `verification_curl` с теми же ссылками на файлы.
