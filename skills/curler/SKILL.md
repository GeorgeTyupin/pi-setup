# Локальные HTTP-проверки

Единственный источник правил для основной сессии и агента `curler`. Тесты, ревью, исправления и подъём окружения не входят в задачу.

## Вход и запуск

Прочитай [общий контракт исполнения](../verify/references/execution.md), если его ещё нет в контексте. Без флага режима спроси через `ask_user_question`; рекомендуй основную сессию. Effort не спрашивается и не переключается.

При запуске из `verify` используй готовые параметры. Агент получает явный `fresh`: только сценарии, нужные пути/адреса, ограничения и сведения об уже полученных разрешениях. В агенте выполняй только разделы ниже, без других агентов и повторного routing.

## Исполнительская часть

1. Возьми методы, пути, ожидания и ограничения из задания. При необходимости прицельно прочитай относящиеся к ним контракт/обработчики. Не считай неизменённую OpenAPI-спеку доказательством отсутствия изменений поведения в других слоях.
2. Назови сценарии и подтверждённый адрес приложения: только HTTP(S) `localhost`, `127.0.0.1`, `::1`. Не угадывай порты, контейнеры или названия БД. Если приложение не запущено, сообщи blocker, не поднимай его сам.
3. До изменяющего запроса опиши последствия и получи явное разрешение, если оно ещё не дано. Чтения могут идти параллельно; зависимые мутации упорядочивай. Не используй общие данные одновременно с тестировщиком без изоляции.
4. Определи схему авторизации по заданию, контракту ручки и уже принятым решениям. Для явно публичной ручки выбери `authMode: "none"`: JWT, credential-файлы и PAIW-указатель не нужны. Не запрашивай их ради требования инструмента. Если необходимость авторизации неизвестна, уточни её, не подменяй отсутствие credentials выбором `none`. Уже подтверждённую схему повторно не согласовывай.
5. Разреши выбранную схему через `verification_auth`. Для `none` передай только `authMode: "none"`; инструмент не ищет credentials. Для JWT (`jwtFile` → `Authorization: Bearer`) или иной схемы передай известный `configFile` или ссылки на credential-файлы. Без явных ссылок инструмент может искать metadata-указатель локального PAIW и затем персонального PAIW; весь workspace не сканируй. Формат указан в [инструкции runtime](../../extensions/verification-runtime/README.md). Модель **никогда** не читает, не декодирует и не копирует credentials. Не используй read/grep/cat, shell substitution, переменную с напечатанным токеном, `.env` или вывод env. Не проси секрет в чате.
6. Если ручке нужна авторизация, но нет JWT/файла, иной схемы, дополнительного заголовка, cookie или прав — остановись и запроси схему и **пути к файлам** недостающих credentials. Не придумывай их и не заменяй пустым/демо-токеном. Для явно публичной ручки отсутствие credentials не является blocker. Не переходи на `none` из-за ошибки credentials или неожиданного 401/403: останови связанные сценарии и сообщи blocker, без обходных повторов.
7. Выполни каждый согласованный запрос через `verification_curl`. Передавай URL, метод, ожидание, безопасное тело через `bodyFile`, выбранный `authMode` и, только если нужны, file references. Для явно выбранной схемы без авторизации передай `authMode: "none", authApproved: true`, без credential-файлов; для иной схемы — `authMode: "headers"` и именованные `headerFiles`. `mutationApproved: true` и `authApproved: true` отражают уже полученное разрешение, а не заменяют его. Для `none` основание — подтверждённое задание, контракт или решение о публичности ручки; отсутствие файлов само по себе не является разрешением.
8. Используй только очищенный результат инструмента. Исполнитель сам загружает секрет внутри кода, передаёт curl приватный файл заголовков, запрещает внешний адрес/redirect и удаляет сырые ответы и временные credentials. Не обходи его прямым bash/curl/HTTP-клиентом. Если runtime недоступен, сообщи blocker и предложи `/reload`, не раскрывай JWT ради fallback.

## Границы и отчёт

Не исправляй код, не запускай тесты, миграции, генерацию, контейнеры или другие скиллы/агентов. Не меняй Git, не обращайся к прод/стейджу. Не читай raw credential-файлы, не используй `curl -v`, tracing, внешние redirect, отключение проверки TLS или публичную выгрузку логов. Согласованные локальные мутации не дают разрешения на прочие изменения данных.

Верни короткий отчёт текстом в чат, без создания файла отчёта, обычно 3–7 строк. Начни со статуса, области и краткого вывода. Для сценария укажи `METHOD /path`, ожидание, фактический HTTP-статус, exit code транспорта и очищенный результат; не заменяй это ссылкой на файл. `passed` относится только к совпавшим выполненным сценариям; `failed` — расхождение/транспортная ошибка; `blocked` — отсутствующая среда/авторизация/разрешение; `skipped` — невыполненное. Ограничения, разрешённые изменения данных и `stale` отметь отдельно.

Для воспроизведения укажи параметры `verification_curl`: выбранный `authMode` и, если нужны, ссылки на файлы без значений credentials. Ручные/Postman-шаги можно предложить, но не представлять выполненными. Пиши по-русски, коротко, без секретов.
