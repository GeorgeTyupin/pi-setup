# Flow

Общий порядок совместной работы над задачей. Не требует конкретного языка, трекера, PAIW или схемы каталогов. Рабочий скилл может добавить чтение задачи и проектные соглашения, но не должен дублировать этот порядок.

## Применить структуру проекта

Не начинай каждый вызов с исследования архитектуры. Используй следующий приоритет:

1. **Применимые `AGENTS.md` и другие явные инструкции проекта.** Если в них заданы слои и зависимости, следуй этой структуре, даже если она отличается от варианта по умолчанию. Не предлагай заменить её стандартной и не спрашивай повторного согласования архитектуры.
2. **Уже установленная структура текущего проекта**, если инструкции её не определяют. Используй подтверждённые ранее соглашения и решения пользователя из контекста или существующего плана без повторного анализа.
3. **Вариант по умолчанию ниже**, если нет заданной или ранее установленной структуры. Не исследуй весь проект только для подтверждения этого варианта.

Инструкции загрузи один раз при входе в проект, если их ещё нет в контексте. Не перечитывай неизменённые документы на каждом треке. Возвращайся к ним при смене проекта, известном изменении инструкций или обнаруженном противоречии. Поиск конкретных мест для правки не равен повторному анализу всей архитектуры.

Дополнительные образцы и границы исследуй только при обнаруженном расхождении, недостатке информации или прямом требовании инструкций проекта. Если код расходится с документацией, сначала проверь относящиеся к этой области инструкции; не выбирай новый порядок молча. Вопрос пользователю нужен только для неразрешимого противоречия или нового решения, а не для повторного подтверждения уже заданных слоёв.

Набор слоёв может отличаться: проект вправе добавлять, убирать, объединять и переименовывать их. Применяй уже заданные изменения автоматически. Незаданные изменения архитектуры по собственной инициативе сначала обсуди.

**Неизменное направление проектирования и реализации: сверху вниз, от потребителя к его зависимостям.** Сначала определяем вход и ожидаемое поведение, затем реализуем нижние слои под эти ожидания. Не переходи на порядок снизу вверх молча, даже ради промежуточной сборки.

Вариант по умолчанию, если проект не задаёт другую структуру:

1. Внешний контракт и его генерация, если применимо.
2. Входная точка: handler, controller или аналог; интерфейс вызываемой операции.
3. Прикладная операция и общие доменные правила: usecase/service или аналоги; интерфейсы необходимых зависимостей.
4. Нижние адаптеры: storage, внешние клиенты и необходимые изменения схемы хранения.
5. Сборка зависимостей.
6. Тестовое покрытие сценария.

Это резервный вариант, не обязательная архитектура. В плане достаточно кратко назвать применяемую последовательность и её источник; не устраивай отдельный выбор архитектуры при каждом запросе. Тесты выделяй завершающим этапом по умолчанию; явные проектные правила их размещения применяй без повторного согласования. Согласование правок трека остаётся обязательным независимо от источника структуры.

## Границы и интерфейсы

- Описывай ожидания на стороне потребителя: только нужные операции, входные данные, результат и ошибки. В проектах с интерфейсами зависимостей их объявляет потребитель, если проект не требует другого соглашения.
- Затем реализуй поставщика под эту границу. Не добавляй нижнему слою методы на всякий случай и не расширяй интерфейс до всего API поставщика.
- Соблюдай разрешённые зависимости проекта. Не смешивай транспорт, бизнес-решения и хранение ради удобства одного трека.
- Готовые слои не переписывай для соблюдения порядка: проверь их совместимость и отметь как существующую основу. Отдельные ветки и перенос основы требуют отдельного согласованного Git-флоу.
- На промежуточном этапе верхний слой может ещё не иметь реализации зависимости. Сообщи об этом; не добавляй искусственные заглушки и не меняй согласованную архитектуру ради сборки. Если проект запрещает такое промежуточное состояние, согласуй более крупный трек с тем же направлением работы внутри него.

## Подготовить треки

До правок кода получи постановку задачи из доступного источника, уточни недостающие требования и сопоставь их с подтверждёнными местами в проекте. Не выдумывай файлы, API и инструменты.

Покажи:

- цель и ожидаемое поведение;
- открытые вопросы, зависимости и риски;
- применяемую последовательность сверху вниз и её источник, без повторного обсуждения заданной архитектуры;
- треки с результатом, затронутыми файлами, причиной изменений и явными границами;
- что уже готово и какие проверки потребуются в конце.

Трек является границей совместной работы, а не будущего коммита. Делай его достаточно крупным для содержательного результата; не выделяй каждую функцию, ошибку или интерфейс в отдельный трек. При этом не объединяй весь план в один автоматический проход.

Если проект предусматривает хранение планов, следуй его правилам. Иначе план в чате достаточен: не создавай PAIW или другую инфраструктуру автоматически. При обновлении сохраняй прогресс, решения пользователя и ручные заметки. Изменения порядка или состава треков по собственной инициативе, не заданные инструкциями и не разрешённые пользователем, сначала согласуй.

## Выполнять по одному треку

План является предложением, а не разрешением на реализацию. Не начинай писать код по итогам разбора, даже в авто-режиме.

Для каждого трека:

1. До правок объясни идею, ожидаемый результат, выбранный способ, интерфейсы, файлы и то, что сознательно не меняется.
2. Остановись и дождись явного разрешения на этот объяснённый трек. Если его уже явно разрешили после объяснения, не спрашивай повторно. Команда "следующий трек" разрешает только объяснение, не правки.
3. Реализуй только разрешённый трек, двигаясь сверху вниз. Генерацию выполняй как часть согласованного трека только известной проектной командой; не редактируй сгенерированные файлы вручную.
4. Покажи изменённые файлы, суть результата, оставшиеся зависимости и состояние проверок. Не утверждай, что код собирается или тесты проходят, если их не запускал.
5. Остановись. Следующий трек, проверки и коммиты требуют отдельной команды пользователя.

Если выяснилось, что нужны изменения вне согласованного трека, новая зависимость или выбор с последствиями для поведения, сначала обсуди это. Не расширяй объём молча.

## Проверки и Git

Написание тестов и их запуск являются разными действиями. Не запускай тесты, сборку, vet и другие проверки автоматически; выполняй их по отдельному запросу с соблюдением инструкций проекта. Состояние проверки из кэша не выдавай за свежий успешный запуск.

Скилл не разрешает создавать или переключать ветки, делать stash, reset, коммиты, push или MR. Эти действия выполняются только по отдельному явно согласованному сценарию и его правилам. Не запускай другие скиллы, субагентов или инфраструктуру автоматически.
