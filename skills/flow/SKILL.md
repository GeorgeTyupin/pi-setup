# Flow

Общий порядок совместной работы над задачей. Не требует конкретного языка, трекера, PAIW или схемы каталогов. Рабочий скилл может добавить чтение задачи и проектные соглашения, но не должен дублировать этот порядок.

## Применить структуру проекта

Не начинай каждый вызов с исследования архитектуры. Используй следующий приоритет:

1. **Применимые `AGENTS.md` и другие явные инструкции проекта.** Если в них заданы слои и зависимости, следуй этой структуре, даже если она отличается от варианта по умолчанию. Не предлагай заменить её стандартной и не спрашивай повторного согласования архитектуры.
2. **Уже установленная структура текущего проекта**, если инструкции её не определяют. Используй подтверждённые ранее соглашения и решения пользователя из контекста или существующего плана без повторного анализа.
3. **Вариант по умолчанию ниже**, если нет заданной или ранее установленной структуры. Не исследуй весь проект только для подтверждения этого варианта.

Инструкции загрузи один раз при входе в проект, если их ещё нет в контексте. Не перечитывай неизменённые документы на каждом треке. Возвращайся к ним при смене проекта, известном изменении инструкций или обнаруженном противоречии. Поиск конкретных мест для правки не равен повторному анализу всей архитектуры.

Дополнительные образцы и границы исследуй только при обнаруженном расхождении, недостатке информации или прямом требовании инструкций проекта. Если код расходится с документацией, сначала проверь относящиеся к этой области инструкции; не выбирай новый порядок молча. Вопрос пользователю нужен только для неразрешимого противоречия или нового решения, а не для повторного подтверждения уже заданных слоёв.

Набор слоёв может отличаться: проект вправе добавлять, убирать, объединять и переименовывать их. Применяй уже заданные изменения автоматически. Незаданные изменения архитектуры по собственной инициативе сначала обсуди.

**Неизменное направление проектирования и реализации: сверху вниз, от потребителя к его зависимостям.** Сначала определяем вход и ожидаемое поведение, затем реализуем нижние слои под эти ожидания. Не переходи на порядок снизу вверх молча, даже ради промежуточной сборки.

Вариант по умолчанию, если проект не задаёт другую структуру:

1. Внешний контракт и его генерация, если применимо.
2. Входная точка: handler, controller или аналог; интерфейс вызываемой операции.
3. Прикладная операция и общие доменные правила: usecase/service или аналоги; интерфейсы необходимых зависимостей.
4. Нижние адаптеры: storage, внешние клиенты и необходимые изменения схемы хранения.
5. Сборка зависимостей.
6. Тестовое покрытие сценария.

Это резервный вариант, не обязательная архитектура. В плане достаточно кратко назвать применяемую последовательность и её источник; не устраивай отдельный выбор архитектуры при каждом запросе. Тесты выделяй завершающим этапом по умолчанию; явные проектные правила их размещения применяй без повторного согласования. Согласование правок трека остаётся обязательным независимо от источника структуры.

## Границы и интерфейсы

- Описывай ожидания на стороне потребителя: только нужные операции, входные данные, результат и ошибки. В проектах с интерфейсами зависимостей их объявляет потребитель, если проект не требует другого соглашения.
- Затем реализуй поставщика под эту границу. Не добавляй нижнему слою методы на всякий случай и не расширяй интерфейс до всего API поставщика.
- Соблюдай разрешённые зависимости проекта. Не смешивай транспорт, бизнес-решения и хранение ради удобства одного трека.
- Готовые слои не переписывай для соблюдения порядка: проверь их совместимость и отметь как существующую основу. Отдельные ветки и перенос основы требуют отдельного согласованного Git-флоу.
- На промежуточном этапе верхний слой может ещё не иметь реализации зависимости. Сообщи об этом; не добавляй искусственные заглушки и не меняй согласованную архитектуру ради сборки. Если проект запрещает такое промежуточное состояние, согласуй более крупный трек с тем же направлением работы внутри него.

## Подготовить треки

До правок кода получи постановку задачи из доступного источника, уточни недостающие требования и сопоставь их с подтверждёнными местами в проекте. Не выдумывай файлы, API и инструменты.

Выбирай число и границы треков с учётом одновременно размера задачи и связности её частей. По умолчанию предпочитай делить работу на осмысленные треки:

- Крупную задачу разделяй, даже если её части связаны: выбирай последовательные этапы с понятными промежуточными результатами.
- Небольшую задачу тоже разделяй, если в ней удобно выделяются треки. Малый размер сам по себе не причина выполнять всё вместе.
- Небольшой тесно связанный объём выполняй вместе, если разделение создаёт искусственные границы и лишние переходы.

Треки не обязаны быть независимыми: результат одного может быть основой следующего. Они могут относиться к исследованию, выработке решения, реализации или проверке. Деление по слоям допустимо, но не обязательно — выбирай границы по устройству конкретной задачи, включая задачи без слоистой архитектуры.

Размер задачи определяет необходимую степень дробления, а связность частей помогает выбрать границы треков. Не дроби ради количества, но и не отказывайся от удобного разделения только потому, что задачу можно выполнить за один проход.

Общий план должен быть кратким и содержательным и в файле, и в чате. Он позволяет понять смысл каждого трека и выбрать, к какому приступить, но не раскрывает заранее его реализацию.

В начале кратко обозначь цель задачи, готовую основу и применяемую последовательность сверху вниз с её источником. Отметь только существенные открытые вопросы, зависимости, риски и необходимые проверки.

Для каждого трека укажи:

- **Название и статус.** Новый трек является предложенным, пока пользователь его не согласовал.
- **Цель.** Что меняется и зачем это нужно.
- **Идею правки.** Основной подход, позволяющий понять смысл изменения, без разбора отдельных функций.
- **Файлы.** Конкретный список затрагиваемых файлов; предлагаемые новые файлы обозначай явно. Для существующего кода при необходимости укажи точку изменения.
- **Результат.** Какое поведение или готовую часть задачи получим после трека.
- **Границы и зависимости.** Только если без них можно неверно понять объём или порядок работы.

Не заменяй содержательный трек пустым заголовком или одним списком файлов. Если нужны шаги внутри трека, формулируй их как короткие действия с результатом. Трек является границей совместной работы, а не будущего коммита: не дроби каждую функцию, ошибку или интерфейс в отдельный трек и не стирай содержательные границы между треками.

Сигнатуры, подробные интерфейсы, устройство отдельных функций, наборы тестовых данных и развёрнутые обоснования не входят в общий план. Раскрывай их по необходимости только по явной просьбе пользователя при переходе к конкретному треку. После общего плана остановись, если пользователь не поручил перейти к разбору или реализации выбранного объёма.

Если проект предусматривает хранение планов, сначала сохрани краткий файл, затем покажи краткий общий план в чате. Иначе достаточно чата: не создавай PAIW или другую инфраструктуру автоматически. Файл и чат могут отличаться формулировками, но состав, порядок, смысл и границы треков должны совпадать. Надстройки над flow используют этот же формат, а не задают отдельные требования к подробности.

Перед сохранением или отправкой проверь содержание: у каждого трека есть идея, файлы и результат; подробный разбор реализации отложен до запроса пользователя; общие инструкции проекта, flow и Git не повторяются. Образец существующего документа используй для оформления, а не как требование повторить его объём.

При обновлении сохраняй прогресс, решения пользователя и ручные заметки. Не дополняй файл подробностями из обсуждения трека, если они не меняют план или не фиксируют важное решение. Изменения порядка или состава треков по собственной инициативе, не заданные инструкциями и не разрешённые пользователем, сначала согласуй.

## Согласовать и выполнить треки

По умолчанию цикл работы: объяснение выбранного трека в чате → обсуждение и уточнения → подтверждение пользователя → реализация → отчёт и остановка. Само обсуждение или согласование общего плана не разрешает правки.

Пользователь может явно поручить выполнить несколько треков или весь план. Это разрешение на указанный объём без повторного подтверждения каждого трека: объясняй треки перед правками и показывай отчёт после каждого, но не останавливайся между уже разрешёнными треками. Определяй смысл поручения по контексту, а не по фиксированным фразам.

Для каждого трека:

1. Раскрой текущий трек в чате: идею, ожидаемый результат, способ, нужные интерфейсы, файлы и то, что сознательно не меняется. Достаточно деталей для решения о правках; уже обсуждённое не повторяй. Переходи к следующему треку только в пределах уже разрешённого объёма или по новой просьбе пользователя.
2. Обсуди возникающие вопросы и уточнения. Если реализация этого трека ещё не разрешена, остановись и дождись подтверждения пользователя. Не запрашивай повторное разрешение, уже данное на этот трек или группу треков. Переход к обсуждению трека сам по себе не разрешает правки.
3. Реализуй только разрешённый трек, двигаясь сверху вниз. Генерацию выполняй как часть согласованного трека только известной проектной командой; не редактируй сгенерированные файлы вручную.
4. Покажи изменённые файлы, суть результата, оставшиеся зависимости и состояние проверок. Не утверждай, что код собирается или тесты проходят, если их не запускал.
5. После отчёта остановись, если следующий трек не входит в уже разрешённый объём работы.

Если выяснилось, что нужны изменения вне разрешённого объёма, новая зависимость или выбор с последствиями для поведения, сначала обсуди это. Не расширяй объём молча.

## Проверки и Git

Полный набор проектных проверок запускай один раз в самом конце: после завершения всей работы по задаче и после последнего коммита последнего трека, если коммиты согласованы. Завершение отдельного трека или группы треков при незавершённой задаче не является поводом запускать весь набор. Если коммиты не предусмотрены, запускай проверки после завершения всех правок.

В финальный прогон включай все предусмотренные проектом проверки: тесты, линтер, сборку, vet и другие применимые команды. Не заменяй полный прогон диагностикой отдельных файлов или проверкой другого репозитория. Соблюдай ограничения проекта на запуск; если нужно отдельное разрешение, запроси его в этот момент, а не пропускай проверки молча.

До финального этапа запускай точечные проверки только по отдельному запросу или прямому требованию проекта. После исправлений по результатам финального прогона и их согласованного коммита повтори полный набор на итоговом состоянии.

В итоговом отчёте перечисли результаты и блокеры всех проверок. Состояние проверки из кэша не выдавай за свежий успешный запуск; без успешного финального прогона не объявляй задачу полностью проверенной.

Скилл не разрешает создавать или переключать ветки, делать stash, reset, коммиты, push или MR. Эти действия выполняются только по отдельному явно согласованному сценарию и его правилам.

В рамках разрешённого трека подключай подходящие наши вспомогательные скиллы автоматически, например правила написания тестов или точечный поиск документации. Отдельная команда пользователя для подключения инструкций не нужна. Не запускай вместо выбранного flow другой самостоятельный flow и не расширяй разрешённый объём. Автоподключение скилла не разрешает запуск субагентов или инфраструктуры.
