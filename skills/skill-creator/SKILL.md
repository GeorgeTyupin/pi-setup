# Создание скиллов этой сборки

Работай только по явному запросу. До согласования плана только читай и обсуждай. Не запускай субагентов, дочерние агенты и другие скиллы автоматически.

## Определить контракт и категорию

Уточни назначение, вводные, результат, доступные инструменты, зависимости и границы разрешений. Проверь существующие скиллы, не создавай дубликат без причины.

Приоритет категории:

1. Явные create, «общий», «обычный» означают общий слой. create work, «рабочий», «для работы» означают рабочий слой.
2. Без явного режима определяй по назначению: обязательные корпоративные credentials, внутренние сервисы, рабочие правила или инфраструктура означают work. Переносимый сценарий без таких зависимостей означает общий слой.
3. При неоднозначности спроси один раз: «Создать общий или рабочий скилл?» Если явный общий режим противоречит обязательной рабочей зависимости, объясни противоречие и уточни решение, не меняй категорию молча.

Общий скилл не должен требовать трекер, PAIW или IDE-плагин без явного объявления этой зависимости. Не копируй управляемые PAIW-источники и сторонние скиллы без проверки прав.

## Размещение и имена

Корень сборки определяется по местоположению этого SKILL.md: два каталога вверх. Это не cwd разрабатываемого проекта и не жёстко заданный путь пользователя. Перед записью прочитай README.md и scripts/components.mjs этой сборки.

- Общий: skills/<slug>/SKILL.md, name: <slug>, вызов /pi:<slug>.
- Рабочий: work/skills/<slug>/SKILL.md, name: <slug>, вызов /work:<slug>.
- Префиксы pi- и work- не добавляй: категория определяется расположением. У Pi единое пространство нативных имён; при конфликте с любым подключённым скиллом предложи другое осмысленное имя и согласуй его.
- Существующие рабочие имена с -oneab сохраняй. Не переименовывай их без запроса.
- Сторонние подключённые скиллы относятся к /other:<name>, их источники не редактируй.

Можно создать каркас командой node scripts/components.mjs new skill <slug> или добавить --work. Команда не заменяет согласование и написание реальных инструкций. В новых скиллах name должен совпадать с каталогом; lowercase, цифры и дефисы, до 64 символов.

Полезные references/, scripts/, assets/ помещай внутри компонента. Используй относительные ссылки. Скилл должен быть реальным каталогом, не симлинком.

## План и содержание

Покажи категорию, пути, изменения, причины и способ проверки. Дождись согласия. Укажи последовательность действий, запреты, необходимые отдельные разрешения, формат результата и условия остановки. Пиши по-русски, кратко.

Минимальный frontmatter: name, description с назначением и условиями применения, disable-model-invocation: true. Автоматический вызов разрешай только по явному запросу пользователя.

Не выдумывай отсутствующие API, инструменты, MCP-имена или возможности агента. Внешние мутации требуют предусмотренного ими согласования. Коммиты, публикации и автоматическую установку инфраструктуры в сценарий не добавляй.

## Проверка

Проверь frontmatter, реальные инструменты, ссылки, отсутствие противоречащих разрешений и рабочих привязок в общем слое. Выполни node scripts/check-portability.mjs. Отдельные записи в .gitignore, manifest и namespace-extension для каждого нового скилла не нужны: они используют каталоги и обнаружение ресурсов.

Для переноса существующего общего компонента доступен /pi:to-work. После изменений предложи /reload. Не называй скилл проверенным в работе, если проверено только его содержимое.
