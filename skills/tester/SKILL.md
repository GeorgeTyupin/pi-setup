# Проверка тестами

Используй только по явному вызову или прямой просьбе прогнать проверки. Ничего не исправляй по результатам.

## Вводные и область

1. Возьми задачу, решения, ограничения и выполненные проверки из диалога. Если данных недостаточно, спроси; внешний трекер не обязателен.
2. Прочитай инструкции проекта и команды в Makefile, package.json или аналогичных файлах. Подтверди базовую ветку и область правки.
3. Учитывай committed diff, staged и unstaged изменения согласно запросу. Читай только нужные части diff для выбора сценариев.
4. До запуска перечисли команды и объясни выбор. Прямая просьба прогнать тесты разрешает соответствующие точечные команды; более строгие правила проекта сохраняются. Для расширения области спроси отдельно.

## Выполнение

- Работай в основной сессии, без субагентов и автоматического вызова других скиллов.
- Проверяй затронутые пакеты и прямых потребителей изменённых интерфейсов. Полный прогон без отдельного запроса не запускай.
- Используй реально существующие команды и раннеры проекта. Для Go при необходимости подходят go test с -run и -count=1, go vet или go build по выбранной области; для других языков бери их собственные команды.
- Сохраняй полный вывод в защищённом временном файле вне репозитория. Сохраняй исходный exit code; tail не должен скрыть падение.
- Независимые проверки можно выполнять параллельно при поддержке раннером и изоляции данных.
- Контейнеры, миграции и изменения БД требуют отдельного разрешения. Если среды нет, сообщи препятствие.
- HTTP-проверки не добавляй автоматически. Для них доступен /pi:curler по отдельному запросу.
- Фронт проверяй только при известном пути и согласованной области. Ручные шаги не представляй как выполненную UI-проверку.

## Границы и отчёт

Не меняй код, не создавай тесты, не выполняй commit, push, checkout, reset, stash, кодогенерацию или внешние мутации. Не ходи в прод и стейдж. Не читай секретные конфиги ради разведки и не выводи секреты.

Покажи область, команды, exit codes, результаты и существенные ошибки; ранее выполненные проверки; что не удалось проверить и почему; ручные шаги при необходимости. Вердикт относится только к выполненным проверкам. Падение назови, код не исправляй.
