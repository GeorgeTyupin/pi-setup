# Запуск тестов

Единственный источник правил запуска тестов для основной сессии и агента `tester`. Написание тестов — другая задача, не часть этого скилла.

## Вход и запуск

Прочитай [общий контракт исполнения](../verify/references/execution.md), если его ещё нет в контексте. Без флага режима спроси через `ask_user_question`; рекомендуй основную сессию. Effort у тестировщика не спрашивается и не настраивается.

При вызове из `verify` используй готовый контракт. Агент стартует с явным `fresh`: родитель передаёт область, сценарии, решения и известные команды, не историю чата. В агенте выполняй только разделы ниже, без повторного выбора режима и без других агентов.

## Исполнительская часть

1. Установи задачу, репозиторий/cwd, выбранные файлы/пакеты и проверяемые сценарии из задания. При недостатке данных уточни область, не восстанавливай весь проект по догадкам.
2. Прочитай относящиеся к задаче инструкции проекта и команды тестирования в Makefile, package.json или аналогичных файлах. Учитывай уже выполненные проверки, но не выдавай старый/кэшированный результат за свежий запуск.
3. До исполнения кратко перечисли точные команды и объясни выбор. Вызов этого скилла или выбор тестов в `verify` разрешает соответствующий согласованный точечный запуск; более строгие требования проекта сохраняются. Расширение области и полный suite согласуй отдельно.
4. Запусти **только тестовые команды** затронутой области и при необходимости прямых потребителей изменённого контракта. Для Go возможны реальные проектные `go test` с `-run` и `-count=1`; для других стеков — их существующие раннеры. Не подменяй тесты `build`, `vet`, линтером или генерацией.
5. Сохраняй полный stdout/stderr в приватном временном файле вне репозитория. Фиксируй настоящий exit code тестовой команды: `tee`, pipe или `tail` не должны скрывать падение. Не печатай весь лог в основной чат; найди первую настоящую ошибку и приведи нужные строки.
6. Независимые тесты можно запускать параллельно только при изоляции ресурсов. Не дели БД с одновременно работающим curler. Контейнеры, миграции, подготовка/удаление данных и запуск недостающего окружения требуют отдельного разрешения. Без него верни blocker.

## Границы и отчёт

Не пиши и не исправляй код/тесты, не меняй snapshots/fixtures, Git, генерацию или конфигурацию. Не выполняй curl/HTTP-проверки, не вызывай другие скиллы/агентов, не ходи в прод/стейдж и не читай секретные конфиги ради разведки. При необходимости secrets попроси пользователя безопасно подготовить окружение, не само значение в чате.

Верни короткий отчёт текстом в чат, без создания файла отчёта, обычно 3–7 строк. Начни со статуса и области: `passed` — все выбранные тесты завершились успешно; `failed` — реально упавший тест/команда; `blocked` — тесты не смогли запуститься из-за вводных или среды; `skipped` — явно пропущенная проверка. Далее команды, exit codes, первая ошибка и ограничения; не заставляй пользователя открывать лог ради вывода. Путь к приватному логу давай только по запросу для диагностики. Отдельно отметь `stale` при изменении проверяемых файлов. Падение назови, ничего не исправляй.
