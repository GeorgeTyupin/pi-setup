# Исполнение проверок

Общий контракт для `verify`, `code-review`, `tester` и `curler`. Правила самой проверки находятся только в её `SKILL.md`. Это не Generic Flow разработки: вызов разрешает выбранные проверки, не правки кода и не следующий трек.

## Параметры и ask

1. В основной сессии вызови `verification_options`, передав имя скилла и **исходные аргументы или текст запроса** в `arguments`. Явно названные в текущем запросе параметры передай структурированными полями `mode`, `effort`, `checks`; это не ответы ask, но они тоже снимают соответствующие вопросы. Не придумывай флаги, не удаляй исходные флаги, не подставляй настройки или выбор из другого запуска.
2. Если `verify` вызван с явно названными проверками, передай их в `checks`: `review`, `tests`, `curl`. Иначе неизвестный набор выбирается через `ask_user_question` с `multiSelect: true`. Нужны только проверки текущей задачи, не обязательно все три.
3. Спроси через `ask_user_question` только поля из `missing`. Режим — `agent` или `inline`. Рекомендуемый вариант идёт первым: агенты у `verify`, основная сессия у отдельных скиллов. Это рекомендация, не автоматический выбор.
4. Недостающий effort уточняется **только для ревью и в обоих режимах**; уже явно указанный уровень повторно не спрашивай. Используй `supportedEfforts`, рекомендуя `recommendedEffort`. В меню до четырёх поддерживаемых уровней; другой поддерживаемый уровень можно ввести текстом. Если поддерживается единственный уровень, второй вариант — отменить ревью, не вымышленный effort. Если модель не поддерживает ни одного уровня, остановись с объяснением.
5. Объедини связанные вопросы в один вызов, когда это не задаёт ненужный вопрос. Если ещё неизвестно, включено ли ревью, сначала выбери проверки, затем спрашивай effort. Отмена или пустой выбор отменяет запуск, без fallback на дефолт.
6. При необходимости повтори `verification_options` с теми же `arguments`, явно названными параметрами и ответами только на недостающие вопросы. Если уже `ready: true`, повторный ask не нужен. Не приступай к проверкам, пока `ready` не равен `true`. При противоречии текста и флагов или неподдерживаемом уровне предложи уточнить ввод, не выбирай приоритет и не понижай effort молча.

Флаги: `--agent`, `--inline`, `--effort <уровень>`; только у `verify` также `--checks review,tests,curl`. `--agent` и `--inline` несовместимы. После `--` идёт текст области проверки. Effort у `tester`/`curler` или у `verify` без ревью — ошибка. Секретов в аргументах быть не должно.

Явное «агентом» означает `mode: agent`, «в этой сессии» / «без агента» — `mode: inline`. Явное `high`, «высокий effort» или «на высокой производительности» означает `effort: high`. Не превращай расплывчатое «быстро» или «качественно» в уровень модели: недостающее уточни. Если режим и effort уже известны из текущего запроса, начинай без повторных вопросов о них. Недостающие существенные сценарии, разрешения, пути credentials и окружение всё равно уточняются.

## Контекст и область

До запуска возьми из диалога задачу, принятые решения, сознательные исключения, репозиторий, базу сравнения и область. Не исследуй всё заново и не спрашивай повторно уже подтверждённое. Прочитай недостающие применимые инструкции проекта.

Для ревью учитывай согласованные committed, staged, unstaged и untracked изменения. Не угадывай базовую ветку. До параллельного запуска запиши HEAD и состояние выбранных файлов, включая незакоммиченные изменения; по завершении сравни их снова. При изменении области результат относится к прежнему состоянию и помечается `stale`, а не выдаётся за проверку новой версии. Не создавай ветки/worktree и не делай коммит ради снимка.

## Основная сессия

В `inline` выполни только исполнительскую часть выбранных `SKILL.md`, без повторного выбора режима. Перед ревью вызови `verification_effort` с `action: "begin"` и выбранным `level`; запомни `lease`. После ревью, в том числе при ошибке, вызови `action: "end"` с этим lease. Не меняй глобальные настройки effort и не называй текстовую просьбу «думай high» реальным переключением модели. Runtime дополнительно восстанавливает уровень при завершении/закрытии сессии; ручной последующий выбор пользователя не перетирается.

У `tester` и `curler` effort не спрашивается и не переключается. В `verify --inline` временный effort относится только к фазе ревью, не ко всему запуску.

## Агенты

Делегирование разрешено выбранным режимом `agent`. Используй native Pi `subagent`, не дочерний CLI. При необходимости активируй `subagents_enable`. Найди инструмент в текущем runtime; не выдумывай имена или схему. Если расширение/инструмент недоступны, сообщи blocker и предложи `/reload`, без молчаливого перехода в inline.

Данные исполнителя бери из `executors` результата `verification_options`:

| Проверка | Агент | Явный context |
|---|---|---|
| review | code-reviewer | fork |
| tests | tester | fresh |
| curl | curler | fresh |

Прямой запуск: `subagent({ agent, task, async: true, cwd, options: { context, outputMode: "inline", artifacts: false, maxOutput: { lines: 80, bytes: 12000 } } })`. Не передавай `output` и не выбирай `file-only`: отчёт должен вернуться текстом в чат, а не ссылкой на файл. **Только для ревью** передай `model: reviewModel` из runtime — с настоящим thinking suffix. Не передавай dispatch-поле `thinking`: у pi-subagents оно не задаёт effort агента. Явный fork не заменяй fresh при ошибке.

Для двух-трёх независимых проверок достаточно отдельных async-вызовов в одном батче; отдельный workflow-script или агент-оркестратор не нужен. Не задавай всем детям общий context: он различается по роли. Не подключай watchdog, советы других агентов или автоматические review-loop.

Каждому ребёнку передай самостоятельное задание:
- маркер `execution: child`, абсолютный `skillFile` из runtime; требование прочитать этот файл и выполнить только его исполнительскую часть;
- репозиторий/cwd, HEAD, базу и точную область файлов/сценариев;
- цель, ожидаемые результаты и относящиеся к проверке решения/исключения пользователя;
- подтверждённые команды/адреса/пути, применимые инструкции и уже выполненные проверки;
- границы разрешений, условия остановки и требование короткого текстового отчёта без создания файла.

`tester`/`curler` получают короткий достаточный пакет, **не историю чата** и не копию полного плана разработки. Curler получает только ссылки на credentials и сведения о явно полученных разрешениях. Ревьюер получает fork — снимок истории на момент запуска; новые вводные передай отдельно через supervisor/steer.

В дочерней сессии или при переданном `execution: child`/готовом контракте от `verify` **не вызывай** `verification_options`, `ask` для режима/effort и других агентов. Не запускай routing повторно, даже если в унаследованной истории был `--agent`. Используй исполнительскую часть скилла. Препятствия и новые решения передавай родителю через `contact_supervisor`; при недоступности — верни `blocked`.

## Параллельность и результаты

Распараллеливай только независимые проверки. Тесты и HTTP-сценарии не должны одновременно менять одну БД или состояние приложения. При конфликте выполни последовательно или запроси изоляцию; не поднимай инфраструктуру молча. Основная сессия может продолжать другую уже разрешённую работу, но изменение проверяемых файлов делает результаты потенциально устаревшими.

После запуска async-детей освободи чат. Обычные дети уведомляют о завершении сами: не опрашивай status в цикле и не используй `bg_wait` без причины. Вопрос ребёнка передай пользователю, не принимай за него новое решение.

Отчёт каждого исполнителя верни прямо в чат: обычно 3–7 строк, начиная с `passed`, `failed`, `blocked` или `skipped`, области и краткого вывода. Затем только существенные находки/первая ошибка и необходимые доказательства; не скрывай блокеры ради краткости. Родитель публикует краткий итог по каждому агенту, не заменяя его ссылкой на отчёт. Служебные сессии и приватные логи раннера могут сохраняться автоматически, но читать их нужно только для недостающих подробностей; пользователю не требуется открывать их ради результата. Файлы отчётов создавай только по отдельному запросу. Ошибка запуска агента, падение теста и ошибка приложения — разные причины. `stale` указывается отдельно от результата.

Никто из проверяющих не исправляет код, не создаёт тесты, не выполняет генерацию, commit/push/MR и не меняет внешние системы. Результат не даёт разрешения исправлять найденное. Вердикт относится только к фактически выполненной области; пропущенное не считается успешным.
